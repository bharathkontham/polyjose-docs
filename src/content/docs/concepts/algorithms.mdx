This page describes polyjose 0.2.0.

polyjose recognises the JOSE algorithm identifiers on this page, spelled exactly as in the [IANA JOSE registry](https://www.iana.org/assignments/jose/jose.xhtml). The same identifiers, with the same behaviour, apply in Rust, Node, the Web, Kotlin and Swift.

Recognising an identifier is not the same as accepting it. Every verify and decrypt call takes an explicit allow-list of the algorithms you expect, and a token whose header names anything else fails with `AlgorithmNotAllowed` before any cryptography runs ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)).

## Conformance

> Conforms to RFC 7518: implements every algorithm marked Required or Recommended, except `RSA1_5` and `RSA-OAEP` (SHA-1), which it deliberately omits (see [the security page](/security/not-supported/)).

Where a recipient expects `RSA-OAEP`, use `RSA-OAEP-256` instead, or ECDH-ES for new recipients.

RFC 7518 marks three algorithms Required: `HS256` for JWS ([RFC 7518 §3.1](https://www.rfc-editor.org/rfc/rfc7518#section-3.1)), and `A128CBC-HS256` and `A256CBC-HS512` for JWE content encryption ([RFC 7518 §5.1](https://www.rfc-editor.org/rfc/rfc7518#section-5.1)). polyjose 0.2.0 implements all three. Of the Recommended algorithms, it leaves out `RSA1_5`, which is Recommended- and which RFC 8725 §3.2 tells applications to avoid, and `RSA-OAEP`, which is Recommended+ ([RFC 7518 §4.1](https://www.rfc-editor.org/rfc/rfc7518#section-4.1)) and uses SHA-1.

## Reading the tables

- Each table has one column per operation: **Sign** and **Verify** for JWS, **Encrypt** and **Decrypt** for JWE. **Yes** means the operation is part of 0.2.0.
- RSA keys work in both directions: the private key signs `RS*` and `PS*` tokens and decrypts `RSA-OAEP-256`, and the public key verifies and encrypts. RSA keys can't be generated; import them from a JWK, PEM or DER.
- **No** in both columns means polyjose recognises the identifier only to report a precise error.
- **Specification** gives the section that defines the identifier, then its requirement level: the "JOSE Implementation Requirements" value in the IANA registry. RFC 7518 §3.1, §4.1 and §5.1 set it for the algorithms that RFC defines. A `+` means the requirement is likely to become stronger in a future version of the specification, and a `-` that it is likely to become weaker.
