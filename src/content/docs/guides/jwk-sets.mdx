This page describes polyjose 0.2.0.

An issuer that signs tokens usually publishes its public keys as a JWK Set ([RFC 7517 §5](https://www.rfc-editor.org/rfc/rfc7517#section-5)), a JSON object with a `keys` array, often at the `jwks_uri` of its OpenID Connect or OAuth metadata. A key usually carries a `kid`, so the issuer can rotate keys and a token can say which one signed it ([RFC 7515 §4.1.4](https://www.rfc-editor.org/rfc/rfc7515#section-4.1.4)), but the `kid` is optional ([RFC 7517 §4.5](https://www.rfc-editor.org/rfc/rfc7517#section-4.5)).

## Verify a JWT against a set

`jwtVerifyWithJwks` takes the token, the whole set and the usual validation options (see [Validate a JWT](/guides/validate-jwt/)). The result says which key verified: its `kid` and its `keyIndex` in the set. In Rust, parse the set with `jwk::JwkSet::from_json` and pass `jwt::Keys::Set` to `jwt::verify`.

<Samples id="jwk-sets/verify" />

Fetching and caching the set is your application's job: polyjose never does any network I/O, and never follows a `jku` or `x5u` header. A typical service fetches the issuer's `jwks_uri` over HTTPS at start-up, keeps the set in memory, refreshes it on a schedule, and passes the cached text to every verify call. When a token names a `kid` that isn't in the cached set, it may refetch the set, rate-limited, so that an attacker can't make it fetch on every request. The sample's set is a local file that stands in for that response.

Don't read the token's header yourself to pick a key before verifying. Pass the whole set and let polyjose choose candidates from the protected header, as described below. polyjose has no way to read a token without verifying it: see [Not supported › Decode without verify](/security/not-supported/#decode-without-verify).

## How a key is chosen

For the token's `alg`, polyjose takes the keys of the set that can serve it: the right key type and curve, a JWK `alg` that is absent or equal, a `use` that is absent or `sig`, and `key_ops` that are absent or contain `verify` ([RFC 7517 §4.2–§4.4](https://www.rfc-editor.org/rfc/rfc7517#section-4.2)). If the token's protected header has a `kid`, only keys with exactly that `kid` remain: a key without a `kid` is never a candidate then, even when no key has that `kid`. If the header has no `kid`, every key that can serve the `alg` is a candidate, with or without a `kid`. The candidates are then tried in set order, and the first that verifies wins. When every candidate fails, you get the error of the candidate that got furthest: `InvalidSignature`, then `InvalidKey`, then `KeyAlgorithmMismatch`, with ties going to the earliest key in the set.

- No candidate fails with `NoMatchingKey`, before any signature is checked.
- More than 8 candidates also fail with `NoMatchingKey`, so a token without a `kid` can't make polyjose try every key of a large set. Change the limit with `maxKeyCandidates`.
- Members polyjose doesn't support, such as an unknown `kty` or curve, or members that are invalid, are skipped rather than failing the set ([RFC 7517 §5](https://www.rfc-editor.org/rfc/rfc7517#section-5)).

<Samples id="jwk-sets/no-matching-key" />

`NoMatchingKey`, `MultipleMatchingKeys` and the JWT error codes tell a prober which `kid`s exist and why a token failed. A server should map all of them to one opaque client error, such as `invalid_token` ([RFC 6750 §3.1](https://www.rfc-editor.org/rfc/rfc6750#section-3.1)).

Never allow an `HS*` algorithm when you verify with a set you fetched. A set can mix secret `oct` keys with public keys, and an `oct` key that an attacker published, or could read, would verify tokens they sign ([RFC 8725 §2.1](https://www.rfc-editor.org/rfc/rfc8725#section-2.1), [§3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)). List only the public-key algorithms the issuer uses.

## Bind the set to its issuer

A key set says nothing about which issuer it belongs to. Pass each issuer's set together with that issuer in `issuers` ([RFC 8725 §3.8](https://www.rfc-editor.org/rfc/rfc8725#section-3.8)). Otherwise a token from another issuer whose keys you also trust, or a token you issued for a different purpose, could be accepted. With several issuers, keep one set per issuer and choose the set by the configuration of the endpoint, not by the token.

## Pick a key yourself

`jwksSelect` returns the one key of a set that matches a selector of `kid`, `alg` and `keyUse` (in Rust, `JwkSet::select` with a `jwk::JwkSelector`). Use it to find, for example, the key to encrypt to, or the signing key in a set of your own:

<Samples id="jwk-sets/select" />

A set's order has no meaning ([RFC 7517 §5.1](https://www.rfc-editor.org/rfc/rfc7517#section-5.1)), so a selector that matches more than one key fails with `MultipleMatchingKeys` instead of picking one. No match fails with `NoMatchingKey`.

<Samples id="jwk-sets/select-ambiguous" />

Selecting a key doesn't decide which algorithm it may be used with. Pass the key only to an operation with an allow-list, and when a `kid` comes from an untrusted header, select with an `alg` as well. Give every `oct` key an `alg`, or select it by `kid`: an `oct` key without `alg` matches every symmetric algorithm. The selected key may be private, so call `jwkToPublic` before publishing it (see [Manage keys](/guides/manage-keys/#publish-only-the-public-half)).

## Keep your own private keys in a set

A set may also hold private keys, such as your own RSA-OAEP-256 decryption key with its `d`, `p`, `q`, `dp`, `dq` and `qi`. polyjose keeps private members as imported, for RSA as for EC and OKP keys. Select the key by `kid` and `alg`, and decrypt with it. Before you publish the set, replace every key with its public half:

<Samples id="jwk-sets/rsa-private" />

Never serve the set you keep at a `jwks_uri`. polyjose doesn't refuse a set because it holds a private key, so checking what you publish is up to you.

An RSA private key can serve two jobs: it signs `RS256` to `PS512` tokens and it decrypts `RSA-OAEP-256`. If you keep one for decryption only, or for signing only, set its `use` (`enc` or `sig`, [RFC 7517 §4.2](https://www.rfc-editor.org/rfc/rfc7517#section-4.2)) or its `alg` ([§4.4](https://www.rfc-editor.org/rfc/rfc7517#section-4.4)). polyjose checks both when it signs, verifies or decrypts with the key and when it picks keys from a set, so a decryption key can't be picked to sign a token, and a signing key can't be picked to decrypt one. Use a separate key pair for each job rather than one key for both.

[Security model › JWK Sets](/security/model/#jwk-sets) summarises these rules.
