This page describes polyjose 0.2.0, compared with JOSESwift 3.0.0.

[JOSESwift](https://github.com/airsidemobile/JOSESwift) signs, verifies, encrypts and decrypts JOSE objects with keys held as `SecKey` or `Data`. polyjose's Swift package does the same with keys held as JWK text, and adds a JWT layer, JWK Set selection and the JSON serializations. This page maps each JOSESwift call to its polyjose equivalent.

Apart from the install lines, every code block on this page is a test. Each **JOSESwift** block runs against JOSESwift 3.0.0 and each **polyjose** block against polyjose, in the same test target, which also checks that tokens pass between the two libraries in both directions. The keys are the published RFC example keys or keys generated in the test, so never use them in an application.

## Install and import

Replace the JOSESwift package with polyjose in Swift Package Manager, and depend on the product `Polyjose`:

<Install platform="swift" />

Then replace `import JOSESwift` with `import Polyjose`. polyjose's calls are synchronous and throw `PolyjoseError`; make them off the main actor. Both packages can stay in one target while you move code over: their type names don't overlap.

Check the platforms before you switch. polyjose needs iOS 16, macOS 13 or watchOS 9 and Swift 6 tools, and it has no tvOS or visionOS build. JOSESwift 3.0.0 also runs on older systems and on tvOS and visionOS. polyjose is a Swift package only, with no CocoaPods or Carthage release. See [Swift (iOS)](/start/swift/).

## Issue and validate a JWT

JOSESwift has no JWT layer. A JWT made with JOSESwift is a JWS whose payload you encode yourself, and validating one means checking the signature, then decoding and checking each claim in your own code. polyjose does both steps for you, so this is where you can delete the most code.

A key that can't leave the Secure Enclave can't be exported, so polyjose can't sign or decrypt with it. You can still verify its signatures and encrypt to it with its public key. See [Store keys securely](/guides/secure-key-storage/).

## Behaviour differences

- **The allow-list is required.** JOSESwift's `Verifier` and `Decrypter` each name one algorithm. polyjose's verify and decrypt calls take a list, with no default, and the token's own `alg` is never trusted alone ([RFC 8725 §3.1](https://www.rfc-editor.org/rfc/rfc8725#section-3.1)).
- **`none` is never accepted.** Neither library verifies an unsigned token. polyjose fails with `AlgorithmNotAllowed`, even when the allow-list names `none` ([RFC 8725 §3.2](https://www.rfc-editor.org/rfc/rfc8725#section-3.2)).
- **Keys are bound to their algorithm family.** An RSA key can't be used for ES256, an EC key can't be used as an HMAC secret, and a JWK's `alg`, `use` and `key_ops`, when present, limit what it can do. A mismatch fails with `KeyAlgorithmMismatch` ([RFC 8725 §2.1](https://www.rfc-editor.org/rfc/rfc8725#section-2.1)).
- **Error codes, not error cases.** polyjose reports a stable code string, and its messages never contain keys, tokens, payloads or plaintext.
- **No payload before verification.** JOSESwift's `JWS(compactSerialization:)` exposes `payload` before `validate(using:)` runs. polyjose returns the payload only from a successful verify ([Not supported › Decode without verify](/security/not-supported/#decode-without-verify)).
- **More in polyjose.** JWT validation, the JSON serializations ([RFC 7515 §7.2](https://www.rfc-editor.org/rfc/rfc7515#section-7.2), [RFC 7516 §7.2](https://www.rfc-editor.org/rfc/rfc7516#section-7.2)), Ed25519 and X25519 keys, JWK Set selection and nested JWTs. [Algorithms](/concepts/algorithms/) lists every algorithm.

## Not supported, or different

What JOSESwift 3.0.0 does that polyjose doesn't, and what to do instead. The tests check each of these against JOSESwift's output.

- **`RSA1_5` and `RSA-OAEP`.** polyjose neither decrypts nor encrypts them, even when the allow-list names them: both fail with `UnsupportedAlgorithm`. Move your senders and recipients to `RSA-OAEP-256` or ECDH-ES first. See [Not supported › `RSA1_5`](/security/not-supported/#rsa1_5) and [SHA-1](/security/not-supported/#sha-1).
- **Compression.** A JWE that JOSESwift compressed (`"zip": "DEF"`) fails with `UnsupportedAlgorithm`, because the Swift package is built without compression. Send content uncompressed. See [Not supported › `zip` in bindings](/security/not-supported/#zip-in-bindings).
- **RSA private JWKs with only `d`.** JOSESwift's `RSAPrivateKey` writes `n`, `e` and `d` only. polyjose needs the CRT members as well (`p`, `q`, `dp`, `dq`, `qi`, [RFC 7518 §6.3.2](https://www.rfc-editor.org/rfc/rfc7518#section-6.3.2)) and fails with `InvalidKey`. Export the `SecKey` as PKCS #1 instead, as shown in [Keys you hold as `SecKey`](#keys-you-hold-as-seckey).
- **RSA keys under 2048 bits.** The Security framework still creates 1024-bit keys, and JOSESwift signs and verifies with them. polyjose refuses them with `InvalidKey` ([RFC 7518 §3.3](https://www.rfc-editor.org/rfc/rfc7518#section-3.3)).
- **RSA key generation.** polyjose doesn't generate RSA keys. Create them with `SecKeyCreateRandomKey`, as before, and import them; or use ES256 or Ed25519 for new keys.
- **Secure Enclave and other non-extractable keys.** JOSESwift signs and decrypts through the Security framework, so it can use a `SecKey` whose private part never leaves the device's hardware. polyjose takes every key as a JWK, so it can only use such a key's public half.
- **Custom signers and encrypters.** JOSESwift accepts your own `SignerProtocol`, `VerifierProtocol` and key management implementations. polyjose has no such hook: the algorithms are the ones it implements.
- **Platforms and package managers.** No tvOS, visionOS or CocoaPods, and newer OS minimums; see [Install and import](#install-and-import).

## Checklist

1. Replace the JOSESwift dependency with polyjose and check the OS minimums.
2. Convert each key to a JWK once: `SecKey` exports through PKCS #1 or CryptoKit, `Data` secrets as `oct` JWKs. Store the JWKs in the Keychain.
3. Give every verify and decrypt call an allow-list with exactly the algorithms you use.
4. Replace hand-written claim checks with `jwtVerify` and its `issuers` and `audiences`.
5. Move `RSA1_5`, `RSA-OAEP` and compressed JWEs to `RSA-OAEP-256` or ECDH-ES, uncompressed, before switching.
6. Replace `JOSESwiftError` handling with a switch on `PolyjoseError.code()`.
7. Remove the JOSESwift package once no code imports it.
