This page describes polyjose 0.2.0.

polyjose leaves some algorithms and features out on purpose. Each section below says what is excluded, why, and what to use instead.

Where you can still ask for an excluded algorithm, for example by passing a token or a key that uses it, polyjose fails with the stable error code `UnsupportedAlgorithm` instead of guessing. Error codes are listed under [Errors](/concepts/errors/), and what polyjose does support is under [Algorithms](/concepts/algorithms/).

## RSA key generation and multi-prime keys

polyjose signs with RSA private keys (`RS256`, `RS384`, `RS512`, `PS256`, `PS384`, `PS512`) and decrypts `RSA-OAEP-256` with them. It imports them as JWK, PKCS#8 or PKCS#1 and exports them as JWK or PKCS#8. A few RSA features are still left out:

- **No RSA key generation.** `jwkGenerateForAlg` with `RS256`, `PS256` or `RSA-OAEP-256` fails with `UnsupportedAlgorithm`. Generate RSA keys with your platform's key tools or a hardware key store, then import them.
- **No multi-prime keys.** An RSA private key with more than two primes (a JWK with `oth`, RFC 7518 §6.3.2.7, or a PKCS#1 `multi` key) fails with `UnsupportedAlgorithm`.
- **No private key without its CRT members.** RFC 7518 §6.3.2 says a producer SHOULD include `p`, `q`, `dp`, `dq` and `qi` with `d`. A private JWK that has only `d` fails with `InvalidKey`.
- **No `RSA1_5`**, in either direction: see [below](#rsa1_5).

**Why:** RSA key generation means generating large primes, which has a timing and review surface of its own, and its cost in WebAssembly and on mobile devices hasn't been measured, so polyjose doesn't offer it yet. Multi-prime keys are rarely used with JOSE. A key without its CRT members would need a second, slower private-key path, for no gain in interoperability.

**Instead:** for new keys, generate an EC or OKP key with polyjose (`ES256`, `Ed25519`, or `ECDH-ES` for encryption). Where you need RSA, create the key elsewhere and import it as a two-prime key.

## `RSA1_5`

**Not supported:** the `RSA1_5` key management algorithm (RSAES-PKCS1-v1_5), in either direction. polyjose neither encrypts to it nor decrypts it, and a token that uses it fails with `UnsupportedAlgorithm`.

**Why:** RFC 8725 §3.2 ("Use Appropriate Algorithms") tells applications to avoid all RSA-PKCS1 v1.5 encryption algorithms and to prefer RSAES-OAEP. PKCS #1 v1.5 encryption has a long history of padding-oracle attacks, so polyjose doesn't decrypt it even when you pass an RSA private key.

**Instead:** encrypt to RSA keys, and decrypt with them, using `RSA-OAEP-256`, or use `ECDH-ES`.

## SHA-1

**Not supported:** SHA-1 in any form. polyjose contains no SHA-1 code.

- **No `RSA-OAEP`.** RFC 7518 §4.3 defines `RSA-OAEP` with SHA-1 and `RSA-OAEP-256` with SHA-256. polyjose implements only `RSA-OAEP-256`. A header or JWK with `alg` set to `RSA-OAEP` fails with `UnsupportedAlgorithm`.
- **No SHA-1 thumbprints.** JWK thumbprints (RFC 7638) are computed with SHA-256, SHA-384 or SHA-512. Asking for a SHA-1 thumbprint fails with `UnsupportedAlgorithm`.
- **`x5t` is carried, never computed.** The `x5t` member holds a SHA-1 certificate thumbprint. polyjose passes it through unchanged but never computes or checks it.

**Why:** SHA-1 isn't practically broken inside OAEP, because OAEP doesn't rely on collision resistance. But SHA-1 has been retired almost everywhere else, and leaving it out entirely means one fewer primitive to trust. `RSA-OAEP` is Recommended+, not Required, in RFC 7518 §4.1, so omitting it keeps polyjose conformant to the Required set.

It conforms as follows:

> Conforms to RFC 7518: implements every algorithm marked Required or Recommended, except `RSA1_5` and `RSA-OAEP` (SHA-1), which it deliberately omits (see [the security page](#rsa1_5)).

**Instead:** use `RSA-OAEP-256`, or `ECDH-ES` for new recipients. polyjose can't encrypt to a recipient that accepts only `RSA-OAEP`.

## `zip` in bindings

**Not supported in the Node.js, Web, Kotlin and Swift packages:** JWE compression (the `zip` header, RFC 7516 §4.1.3). These packages are built without compression. Decrypting a token with `zip` in its header, or encrypting with `compress: true`, fails with `UnsupportedAlgorithm`.

**Why:** RFC 8725 §3.6 ("Avoid Compression of Encryption Inputs") says data should not be compressed before encryption, because the compressed size often reveals information about the plaintext.

**Instead:** send JWE content uncompressed. If you must accept compressed tokens from an existing sender, the Rust crate supports `zip` behind its opt-in `deflate` cargo feature, with decompressed output capped at 250,000 bytes by default.

## Decode without verify

**Not supported:** reading the payload of a JWS, or the plaintext of a JWE, without verifying the signature or decrypting with your key. polyjose has no operation that does this, under any name.

**Why:** claims read from an unverified token are claims anyone could have written. RFC 8725 §3.3 ("Validate All Cryptographic Operations") requires the entire token to be rejected when any cryptographic check fails. A helper that skips the check makes it easy to act on such claims by mistake.

**Instead:** verify or decrypt first. The verified result includes the headers along with the payload. If you need the `kid` to pick a key, pass the issuer's whole JWK Set and let polyjose select candidates; the [JWK Sets guide](/guides/jwk-sets/) shows how.

## Out of scope

**Not in 0.2.0:**

- **Ed448 and X448.** The pure-Rust implementations are not yet stable releases. Use `Ed25519` and `X25519`.
- **X.509 certificate chain validation.** The `x5c` and `x5u` members are carried as data. polyjose never validates a certificate chain, and never uses one to pick a key. Validate certificates with your platform's X.509 tools, then pass polyjose the public key you trust.
- **HPKE**-based JOSE algorithms.
- **COSE** (CBOR Object Signing and Encryption).

## Java

**Not supported in 0.2.0:** a Java-friendly API. The Android and JVM package is designed for Kotlin.

**Why:** the package's API uses Kotlin features that Java can't use directly. Members that take Kotlin unsigned integers (`UInt`) get mangled names when seen from Java, and Kotlin default arguments don't exist in Java, so every argument has to be passed. Java code can call the package, but it's awkward in 0.2.0.

**Instead:** call polyjose from Kotlin. See [Android and JVM (Kotlin)](/start/android/).
